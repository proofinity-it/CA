# Documents

What each file in this directory is, and whether it describes something
that exists. The source of truth for behaviour is the code and
`lake exe refhash-test` / `lake exe registry-test`; the top-level
[README](../README.md) is kept current with every release.

| Document | Kind | Status |
|---|---|---|
| [spec.md](spec.md) | specification | **normative** for scheme 1: the bytes of `stmt` / `decl` / `ref`, enough to reimplement them. Test vectors in §12; `python3 -I tools/refhash_ref.py` is an independent implementation written from it. |
| [payload.md](payload.md) | specification | **draft 2, implemented** (`CA.Payload`, `lake exe payload-test`: every `Init` declaration round-trips exactly; `ca pack` / `ca check` write and check node files). The stored form of a declaration in a node file: a ref table per file; units holding the canonical terms with names replaced by slots, from which the ids are recomputed without Lean; decorations naming the slots. Measured size, open questions; no byte-level test vectors yet. |
| [what-it-is-for.md](what-it-is-for.md) | overview | **current.** The uses that need a result, not a file, to be addressable; CA is the addressing layer only. |
| [usage.md](usage.md) | guide | **current.** Using CA in a project: dependency, attributes, statuses, registry generation. |
| [cli.md](cli.md) | reference | **current.** The `ca` command-line tool. |
| [building.md](building.md) | guide | **current.** The two Lake packages, builds, tests, dependencies, versioning. |
| [modules.md](modules.md) | reference | **current.** The library's modules. |
| [scope.md](scope.md) | overview | **current.** Where CA is used, related work, what an address covers and what it cannot. |
| [worked-example.md](worked-example.md) | reference | **current** for Lean v4.35.0 / scheme 1. The README banner computed by hand: every intermediate id of `Nat.add_zero`'s `stmt`, with an `#eval` that reproduces it. |
| [how-it-works.md](how-it-works.md) | overview | **current.** The canonicalize / serialize / hash pipeline, L0 and L1, the name-based hash, and how the registry is generated: attributes, `#ca_registry`, two-tier key, statement cone and cache. |
| [ref-hash.md](ref-hash.md) | reference | **current.** The `stmt` / `decl` / `ref` identity scheme as implemented in `CA.RefHash`, scheme versions, tested properties. |
| [address.md](address.md) | reference | **current** for the `ca address` CLI subcommand and the L0 / L1 canonicalisation levels; superseded by `ref-hash.md` for "what is a declaration's address". |
| [l1-normalization.md](l1-normalization.md) | engineering note | **current** for `--level 1` in the CLI: what reducible `whnf` normalisation does, the native-`whnf` crash, and the micro-batching that avoids it. |
| [registry-protocol.md](registry-protocol.md) | specification | **draft 2.** The registry as a protocol between nodes: relative verification and the derived "proved", objects, checkers and mirrors, merge, signed names, revocation, schemes, network queries, a SQLite file as the published node with Redis as declbuild's live store, a reference-implementation plan, what declbuild does today versus what is required, open questions and sequencing. |
| [registry-design.md](registry-design.md) | design | **partly built.** Attributes, `#ca_registry`, status classification and `meta.json` exist; `sources.json`, resolution (`use`, `resolve%`), caching and cross-project cascade are plans. The banner at the top lists which is which. |
| [decentralized-formal-math.md](decentralized-formal-math.md) | vision | **mostly a plan.** The three roles, the status lifecycle and the dependency model are the intended design; the `ca publish` / `work` / `submit` / `resolve` subcommands and `use` do not exist. |

`banner-light.svg` / `banner-dark.svg` are the README banner (one
theorem, four objects), generated by `banner.py`;
`figure-stmt-dag-*.svg` is the worked example's figure, generated by
`figure-stmt-dag.py`. Both use real values (`Nat.add_zero`, Lean v4.35.0,
scheme 1). Regenerate them if the scheme or the toolchain changes, and
bump the `?v=` query on the image URLs that show them: GitHub caches
README images by URL, so a replaced file at the same path keeps showing
the old picture.

Removed before the first public release: the
original 2026 design brief for a predecessor project
(`mathlib_content_hash_instructions.md`), the March 2026 pitch PDF, and
the two notes merged into `l1-normalization.md`.

Conventions:

- *implemented* / *current*: matches the code at the latest tag;
- *planned*: designed, not built; the top-level README never presents a
  planned feature as available.
